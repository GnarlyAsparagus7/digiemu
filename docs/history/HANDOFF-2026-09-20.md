## State: what works

`python -m emu.dtpanel` with no arguments opens onto the **live firmware UI**
in about a second. Verified end to end under Xvfb, not inferred: `panel 1878`
in the first status line. Page navigation works (SRC → RECORDER etc.), and
shift-click latches for real multitouch.

Two snapshots exist and they are **not** interchangeable:

| file | build flags | used by |
|---|---|---|
| `snapshots/Digitakt_OS1.53/gui.snap` | GUI set + `unblock_except=(frame_sem,)` | `emu.dtpanel`, `tools/guipress.py` |
| `snapshots/Digitakt_OS1.53/ui.snap` | default flags | the older headless tools |

`unblock_except` is part of the checkpoint build manifest, so a snapshot saved
under one policy refuses to open under the other. That is the manifest working
as designed, not a bug.

## What changed this session

**The boot intro.** mk1 and Digitakt II want opposite things, and only DT2's
half was recorded in `emu/pit.py`. DT2 holds every PIT (unblock satisfies the
frame semaphore; a real PIT3 tick would post it twice). mk1's intro *parks* on
that semaphore, and unblock only sees a pend on the way **in**, so it can never
satisfy an already-blocked wait — the PIT3 tick is the only thing that can post
it. Measured from `boot400M.snap`:

| policy | result |
|---|---|
| hold everything | nothing at all for 600M instructions |
| deliver PIT3 **and** let unblock fake the semaphore | intro exits after 77 ticks instead of 180 frames; no OS task runs |
| deliver PIT3, semaphore left alone | **live UI in 100M instructions** (was ~720M) |

Policy now lives in `devices/digitakt.toml`; defaults preserve DT2/DN2:

```toml
[intro]
channels = [3]
unblocks_frame_sem = false
```

**Symbols.** `intro_pit3_isr` = `0x4006c154`, `intro_done` = `0x4006cb92`,
`frame_sem` = `0x41988be4`, `display_sem` = `0x421cd06c`. Unresolved went
**18 → 9** — one signature was blocking nine, because `frame_sem` is an
`Operand` on `intro_done` and `intro_pit3_isr` is narrowed by `frame_sem`.

`intro_done` anchors on the `addq.l #4,a7` at `0x4006cb92`, **not** the `pea`
at `0x4006cb94`. mk1 lacks DT2's leading `clr.w d0`, so anchoring two bytes
earlier is what keeps the shared `Operand(at=4, adjust=-8)` rule landing on the
`pea` operand. `0x4006cb8e`/`0x4006cb90` never execute.

An earlier memory note said these were "DELIBERATELY NOT WIRED… do not fix
without re-measuring." The observation was right (resolving them makes the GUI
hold PIT3); the conclusion was wrong. The fix is a channel-selective hold.

Files touched: `emu/symbols.py`, `emu/device.py`, `emu/gui.py`, `emu/run.py`,
`devices/digitakt.toml`.

**Still in place, deliberately:** `emu/gui.py`'s status line now also prints
`PCSR 0x%04x` and `slept %ss`. Both were added for the investigation below and
are worth keeping. Remove them if the line gets too noisy.

## Open investigation: flicker, the +Drive flash, the slowdown

The user reported the GUI flickering, "+Drive" flashing briefly, and a
slowdown. All three were reproduced and partly explained. **Read the confirmed
list before theorising — several plausible theories were tested and killed.**

### Confirmed by measurement

1. **The flicker is real, in the guest.** The firmware redraws a
   "FACTORY PROJECT ▸▸ +DRIVE…" overlay over the main page, roughly twice a
   second, indefinitely. About 7–10% of untorn frames are the overlay. Both
   framebuffers hold both pages at different times (`tools/buffers.py`), so it
   is **not** a front/back sampling artifact.
2. **+Drive first-boot work does not complete.** On a fresh boot the firmware
   erases 514 groups from sector `0x80000`, writes 2 blocks, reads 2MB back
   (2048 × CMD18, sectors `0x1000`→`0x1ffe`, ending exactly on the `0x2000`
   boundary), then issues **zero** further storage commands — forever.
3. **Nothing is blocked on storage or the coprocessor.** In a 20M window the
   whole system has only three pend sites: the RTOS tick semaphore
   (`0x40002d24`/`0x4399d7c4`), the main task's message queue
   (`0x40001c2a`/`0x4060fc30`), and the display task on `display_sem`. The
   coprocessor port reports `polls=0 words=0 bursts=0` — never touched. The
   machine is **idle**, not stuck waiting. The overlay's draw guard
   (`tst.l $8(a4)` at `0x400e5390`) is simply still set.
4. **`job_pump` (`0x4008e1c4`) never runs**, on a fresh boot too — so it is not
   just snapshot staleness. The symbol is sound: it disassembles to a real
   prologue that loads `a5 = 0x4000168a` (mk1's `pend_b`).
5. **The PIT3 stop is real firmware behaviour, not a harness bug.** With the
   GUI instrumented, `PCSR` reads `0x0000` — the firmware switched the timer
   off itself, after exactly 312 ticks.
6. **The UI does not freeze afterwards.** After 260M instructions (past the
   PIT3 stop) key presses still change the screen. The `display_sem` change did
   not break rendering.

### Killed theories (do not re-derive)

- *Card overlay isn't checkpointed* — it is. `register_esdhc_checkpoint_component`
  registers `components['esdhc']` and `checkpoint_state()` serializes
  `card_overlay`.
- *Erase commands return a bad response* — they don't. The default R1 is
  already `0x00000900` (state=transfer, READY_FOR_DATA).
- *The 4× `post_intro_ips` change causes it* — no. Forced to 18.72M headlessly,
  PIT3 ticks 4× slower as expected but never stops; wall time stays flat.
- *The GUI's pacing sleep causes the slowdown* — no. `slept 0.0s` throughout.
- *The firmware got slower* — no. Headless throughput is **flat** at ~2M
  instr/s across 260M, with `why` always `limit`. The slowdown is GUI-only.
- *An unresolved `intro_park` was letting the intro task spin* — plausible and
  **wrong**. `emu/longrun.py:264` says blocking in that park loop "is what
  frees the CPU once the intro is over", and it was unresolved on mk1, so
  `unblock` was force-satisfying that pend on every iteration. It is now
  resolved at `0x4006cbc0` (found by disassembly, see docs/mk1/06-symbols.md).
  Measured before and after, on both a `gui.snap` resume and a full cold boot:
  **byte-identical results** — same 3594 eSDHC commands, same per-chunk
  overlay counts, `jobs` still 0. The symbol fix is correct and worth keeping;
  it is not the cause of the flicker.

### Real modelled gap found (not the cause, worth fixing)

`emu/esdhc.py`'s `Card.command()` has **no case for CMD35/36/38** (erase),
though the firmware issues 514 erase sequences and the EXT_CSD advertises
`ERASE_GROUP_DEF = 1`. Erase currently zeroes nothing. It can't be this bug
(the card reads as zeros anyway, `image=None`), but it should be implemented:
CMD35 sets erase start, CMD36 end, CMD38 should clear that range from
`card.overlay`.

### The PIT3 stop, explained

A write probe on `0xFC08C000` settles it. The GUI makes **68 writes of
`0x093f`** from `0x400e5d06` — the display module re-arming PIT3 every frame —
and then one write of **`0x0000` from `0x400e5e02`** at 167M. That address is
the display module's own shutdown:

```
0x400e5dfa  clr.w  d0
0x400e5dfc  pea    (0x421cd074)      ; display_sem + 8
0x400e5e02  move.w d0,(0xfc08c000)   ; PIT3 off
0x400e5e0a  move.b #16,(0xfc05001c)  ; INTC2 SIMR — mask source 16 = PIT3
```

Structurally the same sequence the intro uses to release PIT3. Throughput
falls from **12.4M instr/s to 3.9M at exactly that instruction**, so the
slowdown is a *consequence* of the display releasing its timer, not a cause.

### The job worker pool IS created -- an earlier claim here was wrong

Only 4 of 16 `task_create` sites fire **in a window resumed from
boot400M**, and `0x4008E0B0` is not among them. I concluded the pool was never
created. **That was wrong**, and for a reason worth remembering: a resumed
snapshot cannot re-run a site that already fired before it was captured.

The pool is created lazily, behind a C++ singleton guard:

```
0x4002d81e  tst.l  $421f9b78       ; guard
0x4002d824  bne.b  $4002d8a0       ; already built -> skip
0x4002d826  pea.l  $50             ; else allocate 0x50 bytes
0x4002d830  jsr    (a3)            ; allocator
0x4002d836  jsr    $4008e484       ; construct the pool
```

Reading that guard out of the snapshots settles it:

| snapshot | `0x421F9B78` |
|---|---|
| boot60M, boot200M | `0x00000000` — not yet built |
| boot400M, gui.snap, ui.snap | **`0x42A3C530`** — built, pointing at the object |

So the pool is constructed between 200M and 400M of the cold boot and the
object exists. The workers are created and then do not pump.

**This also exposes a flaw in the pend histogram** (`tools/whyblocked.py`): it
counts pends as they happen, so a task that blocked *before* the window never
pends again and is invisible to it. "Only three pend sites" therefore does not
mean "only three tasks are waiting" — it means only three waits were entered
during the window. Do not read it as a census of blocked tasks.

Static chain to it: `0x4008E0B0` sits inside `0x4008DFE0`, whose single caller
is `0x4008E4A4`, inside `0x4008E484`, reached from `0x4002D836` and
`0x401388CA`. `0x4002D810` is referenced exactly once and **as data**, at
`0x4002FE4A` — how a task entry or registered callback looks.

### More killed theories

- *Chunk size* — the previous leading explanation. Run headless at the GUI's
  exact `BUDGET = 400_000` and `ips = 18.72M`: PCSR stays `0x093f`, PIT3 keeps
  ticking. **Not it.**
- *`on_pixel`* — the one build argument gui.py passes that no headless tool
  does. But `emu/hle.py`'s `do_set` is a full HLE replacement that installs on
  `bitmap=True`, which every tool passes; `on_pixel` is only a notification
  inside it and cannot change guest state. On mk1 setPixel is never called.
- *Waiting on DSPI0* — the documentation's best lead (most-referenced block,
  clock-enabled, modelled by nothing). Measured across a whole boot: **DSPI0,
  DSPI1, SSI0, SSI1 and UART9 see zero accesses.** Those 313 references are
  code this path never executes.

What *is* active: GPIO (5393 reads / 5386 writes, 2693 from each of
`0x400E6A90` and `0x400E6AA2` — a bit-bang pair), and EPORT0 read exactly
**514** times from `0x400E2988`/`0x400E29B2` in the storage driver, matching
the 514 erase groups exactly.

### The task census, and three instrumentation traps

`emu/tasks.py` reads its task table from a snapshot's `extra`. The **ladder**
snapshots have one — only the snapshots my own tools wrote had `{}`. Running
it on `boot400M` gives the census three earlier attempts missed:

```
prio 0  0x40068e06  blocked      prio 6  0x4000b266  blocked  <- application
prio 1  0x40068eb6  RUNNING      prio 7  0x4006c2ae  blocked
prio 2  0x4008e4fa  blocked <- job worker   prio 7  0x400d4642  blocked
prio 5  0x400eb516  blocked      prio 8  0x400e0fbc  blocked
                                 prio 9  0x40001184  blocked
                                 prio 10 0x40002cfa  blocked
```

Ten tasks. `tools/taskback.py` names each wait: the job worker is parked at
`pump_wait` (`0x4008e1f4`) inside `job_pump`, and the application task at
`0x4006c2aa` on the intro frame semaphore — correct for a mid-intro rung.

The worker's parked stack gives the semaphore it waits on: **`0x42A3C544`**,
the pool object (`0x42A3C530`, from the singleton guard) plus `0x14`.
`tools/sempost.py` traces every `sem_post`: that semaphore **is** posted,
twice, from `0x4008E468`, and its count settles at 1 — the worker wakes,
consumes one, and re-pends. **It is alive and cycling, not dead.**

**Three times in this investigation my own instrumentation produced a false
negative, always the same shape — hooking an entry point measures entries,
not activity:**

| reading | why it was wrong |
|---|---|
| "jobs = 0" | `job_pump`'s **entry** was hooked; the worker loops *inside* it and never re-enters |
| "only 4 of 16 task_create sites fire" | a resumed snapshot cannot re-run a site that fired before it was captured |
| "only three pend sites" | a task that blocked *before* the window never pends again, so it is invisible |

### The ladder rebuild, and why it changed nothing

`emu/dspboot.py` — the cold-boot path — contains **no reference to `unblock`
at all**, so no pend is force-satisfied while the ladder is built, and
`display_sem` being unresolved could not have starved anything there. The
prediction that a rebuild would differ was wrong, and the log confirms it:
`TASK_CREATE site 0x4008e0b0` fires at `n=228,850,568`, creating the same
prio-2 worker with the same entry as the old ladder.

The old ladder is preserved at `snapshots/Digitakt_OS1.53.preRebuild/`. It
holds the known-good `gui.snap`; keep it until a new one is verified.

### The flicker does NOT settle -- and a fourth sampling trap

At one point the GUI log showed `panel 1873` constant from 220M onward and I
read that as the flicker settling once the display module releases PIT3. It
does not. `tools/uisettle.py`, which counts EVERY untorn frame rather than
sampling one per chunk, finds **574 overlay frames out of 1719 at 400M** -- a
steady ~33%, with no downward trend.

The GUI's `panel` number is a sample taken at a chunk boundary. Reading it as
a census is the same error as the other three, and this one was documented in
my own `flicker.py` docstring before I made it.

### Ruled out with evidence, in addition to the earlier list

- **EPORT0 / the card-busy wait.** The storage driver reads EPORT0 exactly 514
  times, once per erase group, at `0x400E2988`/`0x400E29B2`. Disassembled, that
  is the card-busy handshake: clear EPORT flag 3, enable the pin-3 interrupt,
  read eSDHC `PRSSTAT` (`0xFC0CC024`), `btst #24` on the DAT0 line level, and
  wait on semaphore `0x421CCA44` only if the card is busy. Our model's PRSSTAT
  reset value is `0xFF8800F8`, so bit 24 is set, the card always reads ready,
  and the driver never blocks there.
- **A stale ladder.** A full cold rebuild produces a ladder **identical** to
  the old one at every rung -- same task counts, same priorities, same pool
  guard -- because `emu/dspboot.py` never uses `unblock`.

### Where this actually stands

The emulator **works**: it boots to the live UI, is interactive, and page
navigation responds. What remains is the +Drive overlay redrawing about twice
a second, which makes the GUI look buggy.

Everything about the worker being dead, starved, or uncreated has been ruled
out by measurement. The open question is narrower and better posed than when
this started: **the pool's semaphore is only ever posted by `job_pump` itself
(`0x4008E468`) — one site in the whole image posts an `object+0x14`
semaphore.** So what submits actual work, and what is the +Drive state machine
waiting for? Start there, and hook the *body* of a routine rather than its
entry.

## Traps (cost real time this session)

- **Don't name a tool `dis.py`** — it shadows the stdlib `dis` that `inspect`
  imports, and capstone fails with a confusing circular-import error.
- **`at()` hooks are block-begin.** Hook a block start, not a mid-block
  address. `0x4006cb8e`/`0x4006cb90` never fire; `0x4006cb92` does.
- **Heredocs through `wsl.exe -- bash -c "…"`** get their backticks eaten by
  the outer shell. Write the file on the Windows side and `cp` it in.
- **`pkill -f`** can match your own invoking command line. Use a bracket
  pattern: `pkill -f "flicker[.]py"`.
- **Run one emulator at a time.** Concurrent runs contend for CPU and skew any
  throughput measurement.
- **`spin()` returns `(pc, executed, why)`** — every tool here ignored `why`
  for most of the session. It is worth printing.

### Input latency and the encoder model

- Two delivery bugs, both from the mk1 clock change: the 16-chunk button
  dwell was 1.4 s at 4.68M instr/s (now `PANEL_DWELL_MS = 50`, encoders
  exempt), and `BUDGET` of 400K instructions was four RTOS ticks (now 100K,

  1.70 s -> 0.11 s; 20 detents over 1 s arrive as 20 packets on time.
- Firmware encoder path, read and instrumented: the UART8 parser sums
  deltas per encoder losslessly (`0x400D3B48`), a flush every 4 ticks posts
  one event with the sum clamped to +/-30 (`0x400D36A8`), the UI loop

  RTOS tick, so timing is faithful. The UI applies a velocity-keyed
  acceleration: one isolated `+1` moves TUNE ~0.001, events 320 ms apart
  do nothing, 40 fast detents move 1.62. Push flag verified 0.
- **Open, needs the hardware:** whether one slow physical detent moves TUNE
  by 1.00 (then a detent is several wire units and the GUI should scale)

### The +Drive overlay flicker: diagnosed further, not fixed

- No card traffic at all during it (`tools/sdlog.py`: 0 commands / 120M).
- The progress view calls `0x400920E6`, which returns non-zero, so it is
  not a failing copy; it is a view waiting for a job that never runs.
- `tools/sempost.py`: the job worker's semaphore `0x42A3C544` IS posted,
  twice, from `0x4008E468`, and its count stays 1: **posted, never
  consumed**. The worker never pends (whyblocked sees only tick/queue/
  display). So the worker task is parked and never scheduled after the
  resume; `tools/taskwho.py`'s "never created" is the known resume
  confound (the pool guard proves it exists). Next step is the RTOS side:
  why a task blocked in `pend_b` at snapshot time does not wake on post.
  This is the same territory as loading samples (a real +Drive), which is
  the natural next project; see the assessment in the session transcript:
  persist the card, let the firmware format it, reverse the layout, then

### The ~60-minute idle blank

**Explained: it is the firmware's own screen timeout.** A headless watch
with `view_activate` hooked (`idlewatch.py`) saw the UI activate a view of
class `TimeoutView` (object `0x42BB56C0`) at 59.8 emulated minutes, and the
frame buffer went to 0 lit pixels at 60.2 and stayed there -- matching the
16.92G-instruction blank in the window run exactly. No screensaver string
exists because the view draws nothing; the ms table at `0x40191494` is a
divisions-of-a-day series, unrelated. Treat the blank as expected
behaviour after an hour idle; a key press should dismiss it (inferred
from the class, not measured).
