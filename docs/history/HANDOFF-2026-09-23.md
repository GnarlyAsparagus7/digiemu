## The headline: live audio in real time, and patterns play

On 09-22 audio worked as render-then-play at 4.2% of real time (about 24 s of
wall time per second of sound). Now:

- **The GUI plays audio live at 48 kHz, in real time.** 100% of real time,
  no dropouts, 60-90 ms buffered, measured through the GUI's own emulator
  thread with a stub sound card. The recording correlates -0.994 with the
  loaded sample. Capacity is 1.4x real time on WSL with the sequencer
  running.
- **Patterns play.** STOP, grid-record trigs on steps 1/5/9/13, PLAY: the
  running light moves, TEMPO blinks, and the recording has every hit on a
  0.612 s grid (quarter notes at the project's 98 BPM) at equal level.
  `tools/livecheck.py --snapshot snapshots/Digitakt_OS1.53/loaded-sample.snap
  --pattern` re-checks all of this headless in about 30 s (exit 0 = every
  beat hit).

Details and numbers are in `DIGITAKT-MK1.md` under Audio ("Audio plays
live", "Patterns play"). What it took, in order of what it bought:

1. **`patches/unicorn-2.1.4-m68k-fast-mem.patch`.** Stock Unicorn sends every
   load and store through a C helper once any memory hook exists (our demand
   mapper is one), and its stubbed dirty bitmap sent every store through the
   self-modifying-code check. Hooks are now routed per page. 75% -> 175% of
   real time on the render benchmark.
2. **`patches/unicorn-2.1.4-m68k-digikit-accel.patch`.** ISA_C for the CFV4E
   (FF1 is an instruction, not a hook); a native block budget for the fast
   stepper; the render's software eDMA done natively. `emu/native.py` probes
   for it; without both speed patches the same run is ~9x slower and the GUI
   falls back to render-then-play at 2 kHz.
3. **Batched SSI, fast idle, and a 64M instructions/s emulated clock** after
   the intro (`[audio]` in `devices/digitakt.toml`).
4. **Refused timer ticks now wait** (`emu/pit.py`, `emu/dtim.py`). They used
   to be dropped; under the render's raised IPL most of DTIM3's 30 Hz ticks
   were lost and the UI ran 4 passes a second. Now 30-50.
5. **Software-forced interrupts on INTC0** (`emu/intfrc.py`, new). This is
   what the sequencer was missing. The render counts samples down and forces
   INTC0 source 44 (vector 108, level 5 — a source the RM lists as "Not
   used"); that handler forces source 57 (vector 121, level 2), which reloads
   the countdown. Neither was delivered, so the sequencer never ticked. 157
   ticks a second now: 96 PPQN at 98 BPM.

## Later the same day: headroom (the speed patch)

On a slow laptop (i5-1245U, Windows) live audio ran at 1.05-1.12x real time.
`patches/unicorn-2.1.4-m68k-digikit-speed.patch` (the sixth patch; both
installers pin it) takes the Windows capacity bench from 1.88-1.92x to
2.53-2.59x and the WSL deterministic replay from 1.72-1.97x to 2.69-2.83x,
with byte-identical audio and CPU state. What it does, from a profile taken
inside the library:

- **One helper per MAC** (`mac_fused`) instead of three, each of which synced
  the TCG globals: the EMAC was about a quarter of the run.
- **`NO_MEM_EXIT`**: no exit-request helper call after every guest load and
  store (12%). Those exist so a memory hook that calls `emu_stop` stops at the
  access; none of ours does, so `Machine` turns it on. Stock Unicorn also
  relied on that check to stop at a faulting store; the patch leaves the
  block from the store helper instead, so faults still stop at the faulting
  instruction (`tests/test_unicorn_speed.py` pins both).
- **`NATIVE_RTE`**: QEMU's ColdFire `rte` instead of the Python
  `UC_HOOK_INTR` pop, which stays as the fallback.
- **`NO_HOOK_PC_SYNC`**: memory hooks no longer re-translate the block to
  report the exact PC. GUI only (`emu/gui.py`), and off under
  `DIGIKIT_PIT3_PROBE=1`.

Everything degrades: on a five-patch library `emu/native.py` reports no
options and the Python paths run. `tools/capbench.py` (new) is the capacity
bench: it programs the pattern at real-time pace (pressed unpaced, DOWN
auto-repeats and YES lands in the file browser) and then measures with
pacing off; `--tracks N` programs N tracks and `--screens DIR` saves every
step. It and `tools/livecheck.py` now reuse one card copy in the temp
directory, since a mapped copy cannot be deleted on Windows and every run
leaked 1 GB. Numbers and the remaining profile are in `DIGITAKT-MK1.md`
("More headroom").

**More tracks cost almost nothing.** Eight tracks playing run at 2.46-2.56x
against 2.68x for one on Windows (0-6% in the WSL replay). The firmware
renders every voice every pass whether it plays or not: a guest profile of
the one-track and eight-track replays shows the same functions and the same
169-170M instructions per emulated second. The panel window costs about 3%.
So neither a thread per voice (it would need the voice render run natively)
nor the emulator in its own process has much to win; the levers are per
instruction. Details in `DIGITAKT-MK1.md` ("More tracks cost almost
nothing").


## Evening: the portable Windows app, digiemu (bring your own .syx)

The app is named **digiemu** (the user's choice: it is separate from digikit,
whose emulator it runs). `digiemu-win64-0.1.0.zip` (`tools\build-windows.ps1`,
`packaging/`): unzip, run `digiemu.exe`, Add firmware, Play. The README's
"Windows app" section is the user-facing summary. The pieces, all new:

- **`emu/release.py`** identifies a .syx from its own header (no Unicorn):
  product from the SysEx ids (`sysex_id`/`os_stream_id`, now in each device
  file), version and build from the ELE3 header (the version is a
  right-justified 12-byte field, not 4 bytes), stamp from section 5. Known
  hash, untested release of a known product (runs through a per-firmware
  device-file overlay after confirmation), or unsupported (named, refused).
- **`emu/bootstrap.py`** is the first run as functions, each stage stamped in
  `firmware.json` and skipped when it verifies: extract, card, ladder, intro,
  settle. `tools/introboot.py` and `tools/uisettle.py` are now thin wrappers.
- **`emu/portable.py`** is the launcher (Tk) plus hidden `--worker` modes, a
  lock per firmware folder, checks (space, path length, OneDrive), and the
  CLI (`--add/--list/--rebuild/--reset`).
- **Panel**: `emu/dtpanel.py --save-on-exit` saves `resume.snap` on a clean
  close. Errors now show on the panel instead of leaving "booting..." forever
  (`config.NotFound`/`device.DeviceError` are SystemExit subclasses and
  escaped `except Exception`). Exit codes: 4 incompatible snapshot, 5 snapshot
  would not open.

What the first run had to learn (details: the +Drive notes below):

- **`uisettle` could never settle a first boot.** `panel.Capture` stops at
  4,096 frames and the firmware's first boot takes ~4,100, so the quiet-run
  count froze. It now counts in a streaming frame hook. A blank card settles
  at ~1,250M; a pre-formatted one at 1,050M.
- **Format the sample volume before the cold boot.** The ekFS mount is
  decided once, at ~218.7M, and the firmware never makes the ekFS itself.
  `emu/ekfsformat.py` (the old `tools/ekfsadd.py` formatter) does it. Sector 0
  must stay blank: the firmware reads it at ~229M to decide to install its
  factory project and sounds, from MAIN OS, not from us.
- **Snapshots of a file-backed card carry no card overlay** (`Esdhc`
  flushes, then empties it). Before, a first-boot gui.snap replayed ~3.9 MB of
  settle-time writes over the card on every launch.
- **Acceptance after settle**: the card structure (`check_card`: sector 0
  BEEFBACE, record bit 0, project slot 0, sounds, ekFS) and, for 1.53, RAM
  (`[firmware.acceptance]` in `devices/digitakt.toml`: job error 0, progress
  done == total, sample volume mounted). A rebuild over a card the firmware
  already initialised only needs sector 0 and the ekFS (the user may have
  changed the factory content).
- **Half-installed cards**: if first boot stops after writing sector 0 but
  before the factory copy, later cold boots never retry. `clear_half_install`
  zeroes sector 0 again, but only when nothing vouches for the card and
  record, project 0 and sounds are all still blank.
- **The card is sparse on Windows** (`emu/sparse.py`: `FSCTL_SET_SPARSE`, and
  `FSCTL_SET_ZERO_DATA` for erases); ~6 MB on disk instead of ~0.93 GB.
  Python's `truncate()` on Windows writes zeros, which is why it was never
  sparse.
- **Frozen exe and CFG**: PyInstaller's bootloader enables Control Flow
  Guard, and VCRUNTIME's longjmp fast-fails (0xC0000409) on Unicorn's
  deliberate `Frame = 0`. The spec clears GUARD_CF in both exes after the
  build (the user chose this over a Unicorn patch). The process then has
  python.exe's mitigations.
- **The factory sample library is not in the firmware** (a real device keeps
  it at card sector 0x180000), so `/factory` is empty. Known gap.

Measured: frozen `--add` from the zip, 8.5 min (ladder ~6 min, settle
~2 min), output byte-identical to the dev build; a re-add says "already set
up"; the self-test (7 checks) gates every build; 66 of 69 test modules pass
on Windows (the 3 known environment failures), all pass under WSL 3.12.

## Night: the first run in ~23 s (was 8.5 min)

The user's point: a real Digitakt flashes and boots in seconds, and a
first run measured in minutes defeats using the emulator to test custom
firmware in CI. Where the time went, and what changed (`emu/bootstrap.py`):

- **The ladder ran 400M instructions with a Python hook on every one**
  (`dspboot.run`'s coverage/counting hook, ~6 min). The firmware *parks* at
  ~159M (pc `0x4006932e`): its tasks are up and the intro waits for a PIT3
  tick the cold boot never delivers, so 60% of the ladder was idle spin.
  `cold_boot()` now runs the same machine with `coverage=False` (new
  `dspboot.run` flag; `limit=None` sets up without starting and returns
  `start_pc`) under the native block budget, in 10M chunks, and stops at the
  first chunk that is mostly idle spins (> 1/4 of its blocks) with no task
  created. It saves one snapshot, `boot.snap`. **~2 s.** The stage keeps the
  name `ladder` (stamps, logs, launcher).
- **Intro and settle step block-bounded** (`longrun.spin fast=True`, the
  panel's stepper) and the settle credits idle spins (`fast_idle`). Intro
  ~8 s (80M), settle ~11 s on a fresh card (750M; the factory install) or
  ~1 s on an initialised one. `fast_idle` in the **intro** breaks it (the
  main loop never runs), so the intro keeps the exact idle hook: that hook
  is now its main cost (~10M Python calls), the next thing to take on if
  more is wanted.
- The stage inputs record `cold`, `stepping` and `fast_idle`, so `--add`
  or Rebuild on a folder built the old way reruns the chain (the old
  gui.snap is still valid: until then the folder stays Ready). RECIPE was not
  bumped. A played old-recipe folder re-added with the same .syx loses its
  resume.snap in that rebuild (as any stage-input change does).

Measured (dev tree, this desktop): `--add` 23 s wall from the .syx to "ready",
strict fresh-card acceptance passed; `--rebuild` over the initialised card
13 s ("already initialised" acceptance); the panel from the new gui.snap plays
live audio at 100% real time (240k frames in 5 s, stub sound card). Frozen
`digiemu-console.exe --add` from a fresh unzip of the rebuilt zip: 24 s, and
boot.snap, gui-raw.snap, gui.snap and the card are byte-identical to a fresh
dev-tree run. Tests: `ColdBootTest` (park rule, failure, cancel, never
flushing on failure) and the stubbed chain tests; Windows 66/69 (the same 3
environment failures), WSL 69/69.

## Later: LOAD SAMPLES in the panel

The user asked for a button that opens a file dialog to load one or more
samples into the Digitakt. The firmware reads the card's sample index once,
at mount in the cold boot, and every snapshot carries that index in RAM, so a
running session cannot see new files. The first run's rebuild is ~13 s now,
so the button restarts the machine rather than trying to patch its RAM:

1. `emu/samples.py` `plan()` reads the WAVs and the card (read-only, safe
   while the emulator runs): each file's card name (stem, printable ASCII,
   at most 64 characters -- a cautious limit, not one read from the
   firmware), a `-2`, `-3`... for a name the firmware's own compare
   (`natcmp`: case-insensitive, skips the character after a number) would
   call equal to one already there, and room (directory block, entry limit,
   inodes, blocks). Bad files are named and left out before anything stops.
2. After the user confirms, the panel stops the emulator with the new
   `Emulator.release_card`: flush, save the session, then close the card
   (`_stop_cleanly`). Without that the map pins the file until the Machine
   is collected -- measured: a rename fails with WinError 32 without it and
   succeeds with it.
3. `samples.write()` re-checks names against the flushed card and writes
   (`ekfsformat.add_file`: sample format, content hash, indexes).
4. The panel exits `SAMPLES_ADDED` (6); the worker maps it to
   `EXIT_SAMPLES_ADDED` (8) and drops the resume stamp; the launcher starts
   a Rebuild and opens the panel when it is ready, without asking again.

Checked end to end on a real folder: two synthetic WAVs (44.1 and 48 kHz)
written by `samples.write`, `--rebuild`, and both content hashes sit side by
side in the settled RAM (the mount's sorted hash -> inode index, around
`0x40379f34`); before the rebuild neither is there, and a made-up control
hash never is. The sample rate is kept, as ekfsadd keeps it (the engine reads
the header's rate); **a 44.1 kHz sample's pitch has still not been checked by
ear**. The user's first try crashed the panel worker with 0x80000003 right
after the write (the rebuild they then started by hand worked): the panel
destroyed its window from inside the canvas item's `<Button-1>` binding that
runs LOAD SAMPLES, Tk walked the freed canvas, and Tcl panicked with `alloc:
invalid block`. Reproduced from source with the real panel and a generated
click; it now closes with `after_idle` (`_close_soon`) and exits 6 cleanly.
Also fixed on the way: `Ekfs()` leaked its file handle when a card had
no ekFS, and `wav_info()` now vets a WAV without converting it (a short fmt
chunk is an Error, not a struct.error).

## Corrections to earlier write-ups

- **"The sequencer stalls after nine counts" was wrong about what it
  measured.** `0x4199e70c` is the render's write index (mod 32) into a
  32-record message ring at `0x4199e48c`, advanced when voice state changes;
  it is not a transport counter. The sequencer was not stalling, it was never
  being ticked. `0x4199dc30`/`0x4199dc31` (bytes) are the step and tick.
  `DIGITAKT-MK1.md` Known limits carries the correction; the old text stays
  as the record, and `docs/mk1/11-audio.md` now opens its sequencer section
  with the same correction. (Only documents 01–09 in `docs/mk1` are
  generated; 10 onwards are written by hand, so they can be edited directly.)
- **The software-eDMA segfaults have a measured cause**, and it is probably
  also the 09-21 8-of-8 (blamed then on garbage DMA parameters; not re-run).
  AddressSanitizer: `uc_mem_map` called from inside a memory write hook (the
  software eDMA mapping a page it was about to touch) resizes the TLB under
  the store in progress. Nothing maps from a hook now (rules in the
  `emu/edma_sw.py` docstring).
- `emu/edma_sw.py` ignored SMOD/DMOD; it wraps modulo now (channels 30 and 42
  use it).
- `tools/seqtest.py`'s `TICK_ISR = 0x4006e75a` is 4 bytes into the mk1
  vector-108 handler (`0x4006e756`), not an entry point, and nothing reached
  it because vector 108 was never delivered.
- The `pit.py` class docstring said holding refused ticks "halted the run at
  58.7M"; that attempt predates the non-destructive SR read and retried only
  at timer deadlines. The current version retries every 2048 instructions and
  passes everything.

## No Elektron bytes in the tree

Checked by searching every string (8+ characters) and every embedded byte blob
in the tree against the mk1 image, not by reading:

- **Signatures are digests now.** `emu/symbols.py` held 2,010 bytes of
  firmware code as search keys. Each is now an `H(n, wild, anchor, digest)`:
  length, wildcards, one instruction-sized anchor and 128 bits of SHA-256.
  Resolution on mk1 is identical, all 139 symbols and alternatives.
  `tools/mksig.py` prints the `H` to paste; `tests/test_symbols_hashed.py`
  fails if a literal signature is pasted back in.
- **The GUI draws the project's name**, not the product's wordmark, logo mark
  or tagline.
- **The console's service commands are not listed** beyond the `#HELLO`
  handshake the emulator's console tools use.
- What is left is small and functional: 79 bytes of container and section
  headers in `docs/mk1/01-container.md`, the 72-byte reset-handler fixture in
  `tests/test_early_init_contract.py`, and short quoted UI messages and class
  names.


## CI and merge protection

`.github/workflows/ci.yml` runs two checks on every pull request and every
push to `main`:

- `tests` builds the patched Unicorn (cached per patch set, since the emulator
  refuses stock Unicorn) and runs every test module with no firmware present,
  as a fresh clone would; `tools/ci/run-tests.sh` is the runner.
- `content-guard` (`tools/ci/content-guard.sh`) fails if a `.syx`, snapshot,
  card image, extracted section or other binary media is tracked, or any file
  is over 1 MB -- the things `.gitignore` keeps out and `git add -f` does not.

`tools/ci/protect-main.sh OWNER/REPO` makes `main` require both checks on an
up-to-date branch, a pull request, linear history, and no force-push or
deletion, for admins too. GitHub only allows branch protection on a public
repository or a paid plan.
