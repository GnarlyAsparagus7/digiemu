## The headline: an old conclusion was wrong, and it was load-bearing

This project recorded that audio runs on a coprocessor, that section id 8 is
that coprocessor's image, and that emulating it would unlock both sound and
the sequencer. All three are wrong, and a lot of downstream reasoning rested
on them.

- `0xFC0C8000` is **SSI 1**, a synchronous serial audio interface on the
  ColdFire itself. The earlier scan that reported "zero references to
  SSI0/SSI1" was looking at `0xFC0C0000`, which is the PLL.
  `docs/mk1/03-peripherals.md` had the right address in its own table the
  whole time.
- **Section id 8 is the USB and MIDI interface controller.** Its string table
  names `USB dev task`, `MIDI task`, `Invalid vid/pid` and FreeRTOS's
  `Tmr Svc`. It is not a sample engine.
- The audio engine is ColdFire code: `FUN_40077420` on vector 191, rendering
  into a 512-byte double buffer at `0x4ba8f080` that eDMA channel 54 drains
  into SSI1, computing with the EMAC multiply-accumulate registers.

**The render loop now runs continuously under emulation** and writes silence,
which is correct for a machine with an empty drive. `docs/mk1/11-audio.md`
has the chain and what it took.

The sequencer was re-tested against that live render loop rather than
inherited. It still does not advance — so audio was never what held it, and
the last consequence of the coprocessor mistake is retired. See **Open
roadblocks** below for what replaced the explanation.

## What changed this session

### Ghidra, and what it bought

Ghidra 12.1.3 headless at `/opt/ghidra`, using the repo's own `ColdfireEMAC`
sleigh language, mk1 image imported at base `0x40000400`.
`tools/ghidra/install-linux.sh` sets it up; `Functions.java`, `Listing.java`
and `RefsInRange.java` are the headless scripts. The stock ColdFire language
stops decoding at `movclr`, so do not use it near interrupt handlers.

**Seven of the eight unresolved mk1 symbols resolved**, each added as
`AnyOf(<DT2 rule>, <mk1 rule>)` so Digitakt II is untouched:

| symbol | address | how |
|---|---|---|
| `sf_fixsfsi` | `0x40124c7e` | signature |
| `sf_cmpsf2` | `0x40123b54` | the shared comparison core; its only five callers are wrappers |
| `ui_key_dispatch` | `0x4000b764` | signature |
| `ui_tick_inc` | `0x400d3574` | signature |
| `ui_tick_counter` | `0x439c828c` | operand of the above |
| `transport` | `0x400e8a70` | signature, call sites follow |
| `prio_heads` | `0x4399d758` | operand of `task_create` |
| `sd_capacity` | `0x421cca34` | offset from `sd_flag` |

Method worth reusing: identify a candidate by running it under Unicorn with
known inputs and comparing against host semantics, using the emulator's own
deferral rules. That is how `sf_cmpsf2` was pinned.

`emu/tasks.py` now lists every task from the scheduler's own priority array
rather than from snapshot metadata, so it works on any snapshot.

### The +Drive

**A one-character bug was silently discarding every write over 15 MB.** The
eMMC model packed `EXT_CSD`'s `SEC_COUNT` little-endian; the firmware reads it
big-endian, computed a 30,208-sector card, and `0x400e2bd2` range-checks
`sector >= capacity` and returns -10 **before issuing any command**. So writes
did not fail, they never happened. With the byte order fixed the firmware's own
FORMAT +DRIVE completes: the image grows to 905 MB and all 161 region-level
writes reach the card as CMD25, against 193 calls and 0 commands before.

From there, by driving the firmware's own format rather than guessing:

- the +Drive card map, in `docs/mk1/10-plusdrive.md`
- eMMC ERASE, CMD35/36/38, modelled as merged byte ranges
- **ekFS**, the sample filesystem: superblock, free bitmap, 128-byte inodes,
  directory entries, all read out of the firmware's mkfs and then confirmed
  from the other end off the image
- `tools/ekfs.py`, a read-only reader

### Snapshots

Every snapshot in the ladder carried the pre-fix card capacity, 30,208
sectors. `sd_bringup` runs long before the first rung and a resume never
re-derives it, so only a cold boot could fix it. The ladder was rebuilt: all
six rungs now read 7,733,248 sectors. `emu/esdhc.py` still reasserts the value
on restore and prints when it has to, which is now a safety net for older
snapshots rather than something the shipped ones need.

`tools/introboot.py` **could never save a snapshot at all** —
`dict()` of a list of `(entry, prio, tcb)` triples raises, and the call sat
behind `if args.out and up` so the failure looked like a boot problem. That is
why the shipped `gui.snap` carries an empty task map, and why `emu/tasks.py`
had nothing to list until it learned to walk the scheduler itself.

## Open roadblocks

In the order they block things.

1. **No +Drive writer.** The card layout and a reader exist; nothing writes a
   sample. This is the single blocker on hearing anything, and it also blocks
   any acceptance test for an audio change. It is ordinary work, not a
   research problem: the formats are documented in `10-plusdrive.md`.
2. **What the playhead counts, and why it stops at 9.** This used to read
   "the playhead does not advance"; see the section below, because it does.
   What is open is both the unit and the bound. `0x4199e70c` climbs from 0 to
   9 over the first 130M instructions after PLAY at a 2 kHz audio clock, then
   holds with the transport still on, and STOP does not reset it. Pressing
   PLAY again resumes rather than restarts: the second start gives 10 through
   18, the same nine counts at the same rate. So nine is what one transport
   start gets, not a ceiling. Eight is also the number of audio tracks on a
   mk1, and an empty +Drive is the other obvious suspect; neither is tested.
   Its **time base is SSI1**: instructions per
   increment against audio rate is 33.3M at 1 kHz, 16.25M at 2 kHz and 11.25M
   at 3 kHz, a constant product within 4%. It reaches 9 after 8 increments at
   both 2 and 3 kHz. The **starvation threshold is between 3 and 4 kHz** --
   PLAY arms at 3 and does not at 4.
5. **`tools/uisnap.py` no longer reaches a live UI.** It runs the intro from
   `boot400M.snap` and stops when the main loop is spinning and the panel
   shows more than the intro logo's 367 pixels. It now reports
   `lit=367 mainloop=0` for as long as it is given -- 2.5G instructions on
   the rebuilt ladder, 900M on the old one -- so it is the tool rather than
   the rebuild. The
   `ui.snap` in place was carried across from the old ladder and works, and
   only `tools/dtdrive.py` reads it, so nothing is blocked. `gui.snap`, which
   `tools/introboot.py` builds and everything else uses, reaches the UI in
   100M instructions.
6. **Eleven named peripherals with no model**: DSPI0, DSPI1, GPIO, USB OTG,
   INTC0/1/2, UART9, EPORT0, SCM, CCM. This is a build queue, not missing
   knowledge — every one is identified and reference-counted in
   `docs/mk1/03-peripherals.md`. DSPI0 is both the most-referenced block in
   the image at 313 and clock-enabled, and nothing models it.

## Traps that cost real time

Read these before repeating them.

**A measurement that starves the thing it measures.** The first sequencer
test ran with audio at 48 kHz. An audio interrupt arrives every ~3,120
emulated instructions and the render needs ~18,500, so the user interface
never ran and PLAY was never seen. `transport` stayed 0 for the whole test,
which reads exactly like "PLAY does nothing". Re-run at 2 kHz it arms
immediately. **Any test that presses keys with audio armed has to slow SSI1
down first.**

**Corruption can look like progress.** A linked-form eDMA `CITER` of `0xc009`
was masked with `0x7FFF`, turning 9 iterations into 16,393 and writing 262 KB
through unrelated memory. The render then got *further*. The correct read is
`(raw & 0x01FF) if raw & 0x8000 else (raw & 0x7FFF)`.

**A benchmark that shared its own subject.** A softfloat A/B test reported
identical hook counts in both arms because `symbols.resolve` caches by image
hash, so both arms mutated one profile. Re-run in separate processes the
honest answer was *no* speedup.

**An oracle that compared the wrong precision.** A claim that the firmware's
divide was 1 ULP off came from comparing single-precision firmware output
against double-precision host inputs. The firmware is bit-exact.

**Writing status inside the guest's own write hook.** Setting the eDMA DONE
bit from within the hook let the guest's pending value land afterwards and
erase it. Queue it and apply from the run loop.

**WSL shell quoting.** `wsl.exe -- bash -lc '<script>'` loses its single
quotes on the way through Git Bash, so backticks run as command substitution
and `$VAR` expands. A quoted heredoc delimiter does not save it. Write the
script to a file and run it by absolute path.

## The sequencer advances, and every address we had was a flag

This is the correction the session turned on, and it reverses a conclusion
this project has carried since long before it.

The old note blamed the playhead on the coprocessor. When that turned out to
be a USB controller, the obvious move was to re-test against the now-running
audio engine, and that re-test said the playhead still does not advance. It
was still the wrong test, because it still trusted an inherited address.

So stop naming addresses. Sample 64 KB of sequencer RAM with PLAY pressed and
again idle, discard every word that rises in both arms as a free-running
clock, and test what is left against STOP:

| word | idle | playing | after STOP | what it is |
|---|---|---|---|---|
| `0x4199e70c` | 0 | +9, then stalls | holds, not reset | the only word the transport drives |
| `0x4199dbb4` | 0 | 65536 | 0 | a flag PLAY sets, not a position |
| `0x4199dc2c` | 0 | 1 | 0 | a second transport flag |
| `0x4199dc30` | 0 | 1 | **1** | latches at PLAY and stays after STOP |
| `0x4199dd08` | 0 | 0 | 0 | not involved |

`0x4199dbb4` and `0x4199dd08` are the pair `DIGITAKT-MK1.md` called the
playhead and its source. `0x4199dc2c` and `0x4199dc30` are the Digitakt II
pair `tools/seqtest.py` and `tools/unblock.py` still carry. Every one is a
flag or a latch, and the rule `0x4199dbb4 := [0x4199dd08] + 1` was never
running, because 65536 is not 0 + 1.

Two traps on the way, both of which produced a confident wrong answer that
looked like a finding:

- **A differencing run that measured a wedged machine.** The first version
  armed the audio DMA during the boot loop, before the setup calls that make
  it valid. The boot never finished, PLAY was never seen, and not one word in
  16,384 changed -- which reads exactly like "nothing advances". The harness
  now refuses to report unless it can show the boot completed, the key armed
  the transport, and the window was live.
- **A rising-counter filter that cannot see a wrap.** `0x4199e3c8` passed
  "strictly rising on every sample" with PLAY and failed it idle, purely
  because of where its 32-bit wrap fell, and it looked like a second
  transport counter. It keeps rising after STOP. Only the STOP test told them
  apart.

## The "+DRIVE" overlay: the recorded diagnosis was wrong

`HANDOFF-2026-09-20.md` records that the job worker "is parked and never
scheduled after the resume", and sets the next step as "the RTOS side: why a
task blocked in `pend_b` at snapshot time does not wake on post". Neither
holds.

Hooking writes to `current_tcb` shows the priority-2 worker becoming current
**499 times in 100M instructions**. It is the second busiest task on the
machine. It is not parked, and the RTOS wake path is not involved.

A block profile keyed by the current task says what it is doing:

| phase | where its time goes |
|---|---|
| the first ~60M instructions | the container depacker at `0x400ea964` |
| after that, indefinitely | a block copy at `0x400e88c0` and a glyph bit-scan at `0x400d4146` |

**The depack succeeds, and its input is firmware data rather than card data.**
The call site passes a literal `0x401f44c8`. That blob's 8-byte header
declares 4,323 compressed bytes and a byte sum of `0x00077588`, and the span
sums to exactly `0x00077588`. `0x400ea964` is MAIN OS's own copy of the
container depacker -- it opens `addq.l #$8,a0` to skip that header, the same
8-byte header the container's packed sections carry. It emits **3.0 MB** into RAM across
`0x419d91c2`..`0x41cbba1f`, the destination climbing monotonically with
sane LZ match distances, then stops and never runs again.

**It then loads the payload into live structures.** Sampling the block copy's
arguments shows small records -- 4, 12, 108 and 160 bytes -- copied out of the
depacked region into fresh allocations at `0x430b7518`, `0x430e4a14`,
`0x430f5e5c`, marching upward. That is a factory project being parsed, not a
spin.

**The overlay is a view, installed once.** The guard is `tst.l $8(a2)` at
`0x400e55ba`, and the `pea.l` that pushes `'FACTORY PROJECT \x07\x07
+DRIVE...'` sits at `0x400e55c0`. Each executes **once** in 150M
instructions, yet rendering the frames as text shows that message recurring
in about 6% of them. So it is installed once on the display stack and
redrawn every frame; nothing re-triggers it. The word the guard tests, at
`0x419a69c0`, holds a code pointer (`0x4000a982`, a real routine) and is
**never written** in 120M instructions. Nothing ever takes the handler down.

Counting frames by lit-pixel total, which is how every tool here has
identified this overlay, cannot tell "drawn again" from "still on the stack".
`tools/flicker.py` and `tools/coldwatch.py` both call it "overlay" on that
basis. Read the screen before drawing conclusions from the count.

**Four explanations eliminated, each against a control:**

| ruled out | the control |
|---|---|
| snapshot staleness | a cold boot is identical through 600M instructions |
| the `SEC_COUNT` capacity bug | the rebuilt ladder and the old one flicker identically |
| a blank card feeding the depacker garbage | the input is a firmware address and verifies byte-exact |
| card content in general | a real 905 MB formatted +Drive gives byte-identical results to a blank card: the same 2276 / 3594 / 3723 command counts, and the same 1,024 bytes written |

**Answered: slow, not stuck, and the snapshot is taken too early.**

Watching the view's guard word at `0x419a69c0` across a long resume:

| instructions past `gui.snap` | guard word | overlay frames |
|---|---|---|
| 50M ... 400M | `0x4000a982` | 69-77 of ~220 |
| 450M | `0x400088a6` | 73 of 218 |
| 500M | `0x419a29dc` | **0 of 36** |
| 550M ... 1001M | `0x419a29dc` | **0** |

At about 450-500M the view object is released -- the guard word ends up
holding a TCB address, which is the heap slot being reused -- the overlay
stops, and it stays stopped through a full billion instructions. Rendering
the screen at 475M shows the ordinary main page, 1873 lit pixels, no overlay.

So the +Drive first-boot work **completes**. Nothing is stuck. What is wrong
is when the snapshot is taken: `tools/introboot.py` stops at the first untorn
frame above `--min-lit`, which is the first frame of the main UI and is
roughly 400M instructions before the install finishes. Every resume of a
snapshot saved there replays the tail of that work, and that is the flashing.

**This was already known, and the tool already existed.** `tools/uisettle.py`
was written for precisely this, and its docstring names both overlay draw
sites, `0x400e5398` and `0x400e55c2`. It had never been applied, and the
ladder rebuild earlier in this session used `introboot.py`, which preserved
the problem. Build `gui.snap` with `uisettle.py`, which waits for 120
consecutive clean frames before saving.

Two things the re-investigation established that were not known before:

- **The 20 September diagnosis was wrong.** It records the job worker as
  "parked and never scheduled after the resume" and sets the next step as the
  RTOS wake path. Hooking writes to `current_tcb` shows that task becoming
  current 499 times in 100M instructions.
- **Card content is irrelevant at this stage.** A real 905 MB formatted
  +Drive, with a valid `ekFS` superblock at sector `0x1c0000`, produces
  byte-identical results to a blank card: the same 2276 / 3594 / 3723 command
  counts and the same 1,024 bytes written. The firmware never reads as far as
  the superblock while doing this work.

**What was built and installed.** `tools/uisettle.py`, resumed from the
introboot `gui.snap`:

```
  700M  overlays 1012  quiet-run 12
  800M  overlays 1012  quiet-run 79
  900M  overlays 1012  quiet-run 143   settled
  SETTLED at 900M: 120 consecutive main-UI frames with no overlay
```

The overlay count stops rising at 700M and the run then banks 120 clean
frames. The resulting snapshot is 28.6 MB against the introboot one's 1.45 MB,
because it holds the depacked factory payload and the structures built from
it. It is installed as `snapshots/Digitakt_OS1.53/gui.snap` in both the WSL
repo and `digikit-win`, with the old one kept beside it as
`gui-introboot.snap`.

Verified on the snapshot itself: 0 overlay frames in 97 over 150M
instructions, the guard word left at a reused heap value rather than
`0x4000a982`, and the panel still drives the menus. Verified again through
`emu.dtpanel` on the Windows tree: thirteen consecutive status lines all
reading `panel 1873`, where the same launch before the fix alternated between
1878, 1876 and 1877. The `[esdhc] driver capacity ... (stale snapshot)` line
is gone from that tree too, since the new snapshot descends from the rebuilt
ladder.

`README.md` and `DIGITAKT-MK1.md` now say that `gui.snap` must be saved with
`uisettle.py` and why, because the build instructions previously named only
`introboot.py` and that is how this session reintroduced the problem.

A note on method, since it cost the most time here: every tool in this repo
identifies this overlay by lit-pixel count, which cannot tell "drawn again"
from "still on the display stack". The instruction that pushes the
`FACTORY PROJECT` string executes **once** in 150M instructions while the
message appears on a third of the frames. Read the screen before drawing
conclusions from a count.

## Tests

54 modules, **388 tests, no failures, 26 skipped**. Two assertions the mk1
port had invalidated were fixed this session: the shipped device count, and a
`machinepatch` golden that is specific to Digitakt II 1.15C and was being run
against whatever image was on disk. `unittest discover` cannot load `tests/`
because there is no `__init__.py`, and three sharc modules import a sibling by
bare name, so run with `tests/` on `PYTHONPATH`.

## Where to start

1. Write the +Drive writer. It unblocks sound, and sound unblocks the only
   acceptance test an audio patch can have.
2. Find what writes the live playhead. Sample the sequencer RAM with the
   transport on and off and subtract, rather than trusting either inherited
   address pair.
3. Model DSPI0 if anything needs the panel or the display beyond what the
   current models cover.
