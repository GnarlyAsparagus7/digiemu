# 08 — The coprocessor section (id 8)

Generated by `tools/mk1doc_coproc.py`. Machine-readable:
`facts/coprocessor.json`.

**This document's original framing is retracted; see `docs/mk1/11-audio.md`.**
It was written on the assumption that section 8 is the audio
coprocessor and that the sequencer and sound both wait on it. It is
not, and they do not.

Pulled out as NUL-terminated runs rather than long printable spans --
which is why an earlier scan reported "no strings at all", the Thumb
code around them producing enough junk to bury the table -- section
8's strings read:

    USB PD Task | USB task | USB dev task | MIDI task | Main task
    GPI task | Audio task | Release mute | Computer/Host
    Invalid vid/pid | Tmr Svc
    {"version": "1.00E", "release": "0018"}

`Tmr Svc` is FreeRTOS's timer-service task. This is the USB/MIDI
interface controller, the Overbridge side, with its own FreeRTOS, its
own firmware version and its own upgrade protocol. The sample engine
is ColdFire code.

Its load address is also no longer unknown. After the 4 KB of `0xFF`
padding the header at file `0x1000` reads, little-endian, as pointers
into `0x6004xxxx`; `+0x04` is `0x60042000`, exactly where content
resumes after the second fill run, so the image sits at `0x60040000`
with SRAM at `0x20000000` -- an ordinary Cortex-M map.

The measurements below stand. Only what they were taken to mean has
changed.

## Is it an ARM Cortex-M image?

A Cortex-M image begins with a vector table: word 0 is the initial
stack pointer, word 1 is the reset handler **with bit 0 set**, because
Cortex-M executes only Thumb. Both together are a strong signature.

| test | value |
|---|---|
| word 0 (LE) | `0xFFFFFFFF` |
| word 1 (LE) | `0xFFFFFFFF` |
| word 1 has Thumb bit | True |
| vectors 1–15 with Thumb bit set | 15 of 15 |
| vectors 1–15 pointing inside the image | 0 of 15 |

| all 16 words are padding | True |

**Verdict: INCONCLUSIVE -- offset 0 is padding (0xFFFFFFFF), so there is no vector table here to test**

This section begins with **4096 bytes of `0xFF` padding**. A vector
table test run at offset 0 is therefore meaningless — every word
has bit 0 set, so a naive Thumb-bit check passes on nothing at
all. An earlier version of this tool reported exactly that false
positive; the check now requires vectors to point somewhere real.

Retested at the first non-padding offset `0x001000`:

| test | value |
|---|---|
| word 0 | `0x412000D1` |
| word 1 | `0x60042000` |
| word 1 has Thumb bit | False |
| vectors pointing inside the image | 0 of 15 |

**Verdict: NOT a Cortex-M vector table here either**

## Does it actually disassemble as Thumb?

The evidence above pulls two ways. The Thumb marker counts are
real, but the entropy is ~7.1 bits/byte — high for plain code —
and there are no strings at all. Either it is densely packed code
or it is compressed data that happens to contain those byte pairs.

Disassembly settles it: real code decodes in long unbroken runs,
while compressed data hits an undefined encoding within a few
instructions. So the measure is **run length**, not whether any
single instruction decodes.

| probe offset | bytes decoded before the stream broke (of 4096) |
|---|---|
| `0x001000` | 44 |
| `0x0042BA` | 4094 |
| `0x007576` | 4096 |
| `0x00A830` | 2476 |
| `0x00DAEC` | 692 |
| `0x010DA6` | 76 |
| `0x014062` | 752 |
| `0x01731C` | 4096 |
| `0x01A5D8` | 1124 |
| `0x01D892` | 658 |
| `0x020B4E` | 1366 |
| `0x023E08` | 1696 |

Average unbroken run: **1764.2 bytes**; longest **4096**; probes that
decoded a whole window without breaking: **3 of 12**.

**Interpretation: EXECUTABLE THUMB CODE interleaved with data. The averages understate it: a probe that decodes a whole 4096-byte window without hitting an undefined encoding is something compressed or random data essentially never does, and several probes do. The short runs are probes that landed in a literal pool or mid-instruction, which is normal for ARM firmware and also explains the ~7.1 bits/byte entropy.**

## What is still unknown
