# 04 — The interrupt vector table

Generated by `tools/mk1doc_vectors.py` from `gui.snap`.
Machine-readable: `facts/vectors.json`.

The vector table is the map from hardware event to code, so a vector
pointing at real code is a device the firmware expects to hear from —
which makes this the most direct statement of what an emulator has to
model.

**It is read from a snapshot, not from the image.** VBR is `0x40000000`
and MAIN OS loads at `0x40000400`, so the table sits *below* the image
and is written at run time. It does not exist in the `.syx` at all.

- Vectors read: 256
- Default stub: `0x40001536`, shared by 228 slots
- **Slots pointing somewhere else: 28**

Vector numbering: 0–63 are CPU exceptions; 64+ are interrupt
controller sources, `vector = base + source` with bases 64 / 128 / 192
for INTC0 / INTC1 / INTC2. The bases come from the PIT, DTIM and UART
vector numbers in `docs/contracts/mcf5441x-reference-v1.json`, not from
an assumption.

## Software-forced interrupts

These sources are **not driven by the silicon** — the MCF5441x
manual lists them as gaps — yet each has a real handler installed.
An interrupt nothing can raise in hardware, with a handler on it,
is one the *firmware* raises itself, which is what the INTC force
registers (INTFRCH/INTFRCL) are for.

| vector | source | nominally | handler |
|---|---|---|---|
| 64 | INTC0 source 0 | -- | `0x40001566` |
| 108 | INTC0 source 44 | MAC-NET0 | `0x4006E756` |
| 121 | INTC0 source 57 | MAC-NET1 | `0x4007041C` |
| 134 | INTC1 source 6 | FlexCAN0 | `0x40007044` |
| 191 | INTC1 source 63 | -- | `0x40077420` |

Vector 108 is the sequencer tick. It sits on INTC0 source 44,
which the manual records as an unused gap in the ENET0 block —
so the sequencer clock is raised in software, not by a timer.
That is consistent with the earlier finding that its cadence comes
from an audio sample-clock accumulator rather than from any PIT.
